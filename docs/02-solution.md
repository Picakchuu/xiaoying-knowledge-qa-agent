# 02 · 方案与取舍

## 1. 一句话架构

> 模型只负责「提议下一步动作」，工具负责「给证据」，**代码负责「能不能结束」**。

这条分工是整套设计的骨架：模型可以说"我答完了"，但代码会拿它的引用逐字回原文核对；核对不过就打回去，让它改引用、改答案或转成追问。

```text
用户问题 (+history)
      │
      ▼
┌───────────────────────────── ReAct 主循环 (src/agent.py) ─────────────────────────────┐
│  模型输出 {"action","args","why"}                                                      │
│    ├─ search_docs   → 文档检索（同义词扩展 / 废止过滤 / 冲突线索）                      │
│    ├─ read_chunk    → 读原文片段（引用的唯一合法来源）                                  │
│    ├─ list_versions → 按主题反查版本与 status                                          │
│    ├─ citation_check→ 自检引用（可选，最后仍由代码复核）                                │
│    ├─ answer        → 代码终审：quote 逐字 + 数值 grounding + 未处理冲突                │
│    ├─ ask_user      → 代码检查：是否真的有两份以上互斥原文                              │
│    └─ finish        → 代码降级保护：声明 answered 却没有有效回答 → insufficient         │
│  观察结果写回 history；达到 MAX_STEPS=12 / MAX_TOOL_CALLS=8 → incomplete               │
└───────────────────────────────────────────────────────────────────────────────────────┘
      │
      ▼
JSON 结果 + Markdown 渲染 + trace.jsonl（动作/参数/返回摘要/后续动作/一句话理由）
```

## 2. 为什么不用 Agent 框架（ADK / LangGraph / AgentScope）

- 本题被检验的核心恰恰是**决策循环本身**：模型看到工具结果后有没有改变动作。框架会把这层封装掉，等于把评分点藏起来；
- 动作空间需要严格枚举校验（未知动作、错参数要能打回而不是抛栈），自建 `actions.py` 比框架的默认行为更可控；
- 零重依赖 → 评委一条命令就能跑；离线 mock 不需要任何外部服务。

**代价**（诚实记录）：没有中间件生态，trace 与重试得自己写（约 180 行），换来的完全可见性对本题是划算的。

## 3. 为什么检索用「关键词 + 2-gram + 小同义词表」而不是向量

- 要能**离线复现**：不引入 embedding 模型/向量库，评委无 key 也能跑；
- 要能**断言召回是否改进**：n-gram 打分可解释，改了 query 分数怎么变说得清；向量相似度在这类短语料上不稳定；
- 语料是 9 篇制度/FAQ（约 40 个片段），2-gram 覆盖率 + 标题加权已经够用；同义词表（`src/synonyms.py` 12 条）覆盖了"打车→市内交通费""攒→结转"等口语改写。

**升级路径**：`DocStore.search` 是唯一检索入口，换成 `EmbeddingRetriever` 只需替换这一处，接口与 observation 信封不变（本次不实现，见 `docs/05-retrospective.md`）。

## 4. observation 协议（工具与模型的唯一接口）

```json
{"ok": true, "tool": "search_docs",
 "data": [{"doc_id":"D01","chunk_id":"D01#c2","score":0.85,"heading":"二、报销期限",
           "text":"员工应在费用发生后 30 天内提交报销申请…","version_date":"2025-03-01","status":"active"}],
 "error_code": null,
 "note": "命中 5 段；已过滤 2 段已废止文档；涉及文档：D01《差旅报销制度（2025 版）》、D02《…（2026 修订）》、D02b《…（总部专用版）》；线索：同一时间单位出现不同数值（D01=30天 / D02=15天 / D02b=15天）…",
 "hints": {"conflict_hint": {"unit":"天","values":["15","30"],"candidates":[…]}}}
```

三个刻意设计：

1. **`note` 里给出「涉及文档」清单**：标题里常含「总部专用版」这类范围信息，只给最高分片段会让模型漏掉它（真模型第一次跑就漏了，加了清单后它会主动去查）；
2. **冲突线索触发时，直接附带各来源的「适用范围/总则」片段**（`via=conflict_scope`）：模型不用再为了查范围多发一次检索。实测这一处把 `deepseek-v4-pro` 在冲突题上的 **7 步 / 249 秒压到 2 步 / 59 秒**；
3. **`conflict_hint` 只是线索不是结论**：同一次检索里，两段以上来自不同文档、都含时间类数值、正文至少共享 2 个 2-gram（确认在谈同一件事）才给。它让模型"看得见冲突"，但要不要追问仍是模型的决定；
4. **失败也走同一个信封**：`ok=false + error_code`，工具内部吞掉所有异常。模型看到的是信息，不是调用栈。

## 5. 引用校验：三级，全部可解释

| 级别 | 拦什么 | 失败码 |
|---|---|---|
| quote 存在性 | 凭记忆改写的"原文" | `citation_not_found` / `unknown_citation` |
| 数值 grounding | 引 D01 却说 15 天 | `missing_number_grounding` |
| 未处理冲突 | 同时引了两份互斥来源，却只答一个值 | `unhandled_conflict` |
| 悄悄挑一个（弱模型常见） | 检索线索显示 15 天 vs 30 天，回答只写 15 天且不提适用范围 | `cherry_picked_conflict` |

另外三道代码兜底，都是**真模型实测踩出来后**补的：

| 兜底 | 触发 | 起因 |
|---|---|---|
| 工具失败熔断 | 同一工具连续失败 3 次 → 直接 `failed`，不再让模型空转 | 实测真模型会一直换 query 重试到步数上限，返回 `incomplete` 而不是 `failed` |
| 资料缺口回填 | 回答里出现「未提供 / 未写明」而 `missing` 为空 → 按问题类型补一条缺口 | 实测回答「文档未提供具体价格，请联系销售」但缺口栏是空的 |
| JSON 尾部容忍 | 只取输出里的第一个完整 JSON 对象 | 实测 `deepseek-chat` 会在 JSON 后面再跟一段说明或第二个对象，严格解析会把整轮判成失败 |

最后一条是看了真实退化样本后补的：弱模型会挑"两份都写 15 天"的来源，引用集合内部自洽，
`unhandled_conflict` 抓不到——但上一轮检索的 `conflict_hint` 说库里还有 30 天。
带适用范围词（总部/分支机构/仅适用…）的条件化回答会被放行，避免误杀。

归一化只做**字面层**（NFKC、去空白标点、中文数字→阿拉伯、单位别名 天/日），不做语义判断。所以校验器不会误杀同义改写，但也拦不住"语义上不支持的引用"——这条边界写在 `docs/03-evaluation.md`。

## 6. 冲突处理策略（prompt + 代码双保险）

1. 多来源对同一事项给出不同值 → **先查证**：`read_chunk` 读全文找适用范围，`list_versions` 看版本与 `status`；
2. 能判别 → 条件化答案，同时引用所有相关来源；
3. 不能判别 → `ask_user`，提问里必须写出双方数值与版本日期，`gaps` 说明缺什么；
4. **禁止**：只引一条、默认"新版本优先"、把 30 与 15 折中。前两条 prompt 里明写，第三条由 `unhandled_conflict` 兜住（回答里必须出现两个值）。

同一问题、不同语料会得到不同决策，这是"检索/仲裁真的在起作用"的证据：

| 语料 | 问题 | 结果 |
|---|---|---|
| `conflict_min`（只有 D01/D02） | 报销期限多久？ | `conflict_pending`（两份都没有适用范围，无从判别） |
| `full`（含 D02b 总部专用版） | 报销期限多久？ | 真模型：查证后仍缺"用户所在范围" → `conflict_pending`，但引用里已带上 D02b#c1 |
| `full` | 我是总部员工，报销期限多久？ | `answered`：15 天（D02b#c2 + D02b#c3） |

## 7. 多轮与上限

- 历史以 `{question, answer, status, cited_doc_ids}` 传入；追问时检索偏好带上上一轮主题（Mock 的规则：问题本身已带实体就用问题本身，否则与上文合并）；
- `MAX_STEPS=12`、`MAX_TOOL_CALLS=8` 双上限；超限返回 `incomplete` + 已完成动作列表 + `reason`，**不会**伪造一个答案；
- 模型输出不可解析时不算步数浪费：转成 `bad_model_output` observation 打回一次，连续两次失败才判 `failed`。

## 8. 状态由代码判定

| 状态 | 触发 |
|---|---|
| `answered` | 引用逐字通过 + 数值全部有出处 + 无未处理冲突 |
| `conflict_pending` | `ask_user` 且至少两份互斥引用通过校验 |
| `insufficient` | 检索穷尽/资料缺口；或模型声明 answered 但校验不过且它自己收尾 |
| `failed` | 工具持续失败、模型输出连续不可用 |
| `incomplete` | 触达步数/调用上限 |

## 9. 技术选型与版本

| 项 | 选择 | 说明 |
|---|---|---|
| 语言 | Python 3.13（本机）、>=3.10 语法兼容 | 只用标准库 + `requests` + `pytest` |
| 框架 | **无** | 见 §2 |
| 模型 | OpenAI 兼容端点，默认 `deepseek-chat`；本次实测 `deepseek-v4-pro` | 换模型只改 `.env` 三行 |
| HTTP 客户端 | `requests`（直连 `/chat/completions`） | 不用 `openai` SDK：本机 `openai 1.40` 与 `httpx 0.28` 不兼容（`proxies` 参数被移除），升级依赖又受网络限制；直连少一层依赖，对任何兼容端点都成立 |
| 推理型模型处理 | `MODEL_MAX_TOKENS` 默认 6000 | 实测 `deepseek-v4-pro` 会把 token 先花在 `reasoning_tokens` 上；给太小会出现"空 content"，客户端会明确报错而不是静默丢步 |

## 10. 已知限制（详见 03）

- 校验器只做字面可验证，语义级别的"引用其实不支持结论"拦不住；
- 2-gram 召回对长尾表述仍可能漏（同义词表只有 12 条）；
- 推理型模型的 `reasoning_tokens` 不计入答案质量，但会消耗预算与延迟（单次 1~2.5 分钟）；
- HTTP 封装无鉴权、无并发控制，仅供演示。
